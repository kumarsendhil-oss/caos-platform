## Open questions this spike must answer

These are what ADR 0008 currently assumes. Each needs a real answer, and **"it worked" is not one** — record what came back, per document, with the failure cases named.

1. **Does accuracy hold across different vendor invoice formats?**
   This is the real risk and the actual reason PP-Structure was chosen over Tesseract (raw text only) and DocTR (no table structure recognition). Layout variance is the thing it is being trusted to absorb. A high score on invoices from three vendors says very little; the question is whether accuracy is *stable* across formats or whether it collapses on particular layouts — multi-column headers, line items split across pages, totals inside a bordered box, right-to-left column orders, logos overlapping the header block.
   **Record per-format, not just pooled.** A pooled 92% hiding one vendor format at 40% is the failure mode that matters, because that vendor's invoices arrive every month.

2. **Does the ~1% handwritten assumption match what is actually in the sample?**
   ADR 0008's Context states documents are "~99% printed PDFs (mostly clean invoices) with ~1% handwritten (per discovery)". The EasyOCR fallback is scoped entirely by that number. If the real proportion is 5% or 10%, the fallback stops being a secondary path and becomes a routine one — which changes its priority, and possibly ADR 0008's Consequences.
   Also worth recording: how many documents are **scans** rather than born-digital PDFs. A clean digital PDF and a phone photo of the same invoice are very different inputs, and "printed" does not distinguish them.

3. **Where does EasyOCR's fallback path actually need to trigger, vs. where does PaddleOCR alone suffice?**
   ADR 0008 specifies EasyOCR "specifically for the ~1% handwritten documents". The open question is whether handwriting is the right *trigger condition*. Candidates the real sample may reveal: handwritten documents, low-quality scans, stamped or annotated invoices, and partially-handwritten documents (a printed invoice with a handwritten amount or signature block — arguably the most likely real case, and the one a binary printed/handwritten classifier handles worst).
   The deliverable here is a **trigger rule**, not a score: what observable property of a document should route it to the fallback.

4. **Are the failures recoverable or silent?** *(carried from P0-02 finding #2's shape)*
   A field that extracts as `null` is a Task the agent can raise. A field that extracts as a confident wrong value is a wrong entry in the books. These are not the same failure and the per-field report distinguishes them — count them separately.

5. **What is the actual CPU throughput per document?**
   ADR 0008 accepts CPU-only on the grounds that "document volume is moderate and processing is already asynchronous (ADR 0003) with no real-time latency requirement". Worth confirming against the real target of ~500 GST returns/month: measure seconds per document on realistic inputs (multi-page scanned PDFs, not single clean PNGs) and state what that implies for the queue.

## Secondary observations worth capturing while there

- Whether PP-Structure's **table recognition** finds the line-item table at all on each format, separately from whether it parses the rows correctly. A missed table and a misparsed table need different fixes.
- Whether **GSTIN** failures cluster on specific characters — `0`/`O`, `1`/`I`/`l`, `5`/`S`, `8`/`B`. A systematic confusion is fixable with a checksum-validated correction pass; scattered errors are not.
- Whether **multi-page invoices** are handled (line items continuing onto page 2), and whether the page break duplicates or drops rows.
- Whether the **invoice number** is reliably distinguishable from other document numbers on the page (PO number, challan number, e-way bill number) — this keys CG7's duplicate check, so a confusion here has a direct correctness consequence.
- Whether **rotation/skew** in scans needs `use_doc_orientation_classify` / `use_doc_unwarping` enabled, both of which the harness currently disables for speed.

## Method notes, carried over from the other spikes

These were learned the hard way in P0-02, P0-06 and P0-07 and apply here unchanged:

- **Read back; do not trust a success response.** P0-02's Rule 1. An extraction that returns a value is not evidence the value is right — that is precisely what the ground truth is for.
- **Record the evidence, not the conclusion.** Per-document JSON in the results directory; findings cite specific documents. Note the DPDP constraint on *which* evidence can be committed — see README.
- **Don't generalise from one specimen.** P0-02 finding #18's "minimum case, not the representative one". Here it applies per *vendor format*, not per document.
- **Label what was not tested.** A scope limit stated up front is worth more than a finding that quietly over-claims.
- **Prove the harness before trusting its output.** Done here deliberately, before any real document exists — the synthetic run exercises extraction and scoring so that a real failure is attributable to the documents or the model, not to a bug in the scorer.

## What is blocked, and on whom

**20–50 real invoices across different vendor formats, from the practice.** Format variety is the requirement, not the count — 40 invoices from one vendor is a weaker test than 20 from twenty vendors, because layout variance is the specific thing being validated.

This cannot be fabricated and cannot be substituted with a public dataset without measuring the wrong documents. It is the practice's to provide. The DPDP handling in the README should be confirmed before the first real document is processed, not after.

## Harness verification result

Kept at the bottom, under its own heading, so it can never be mistaken for the Findings section above. **This is a test of the harness, not a measurement of PP-StructureV3.**

Run 2026-09-17. 3 synthetic fixtures (`samples/`), three deliberately different layouts — `classic`, `boxed`, `compact`. CPU-only, `paddle.is_compiled_with_cuda() == False`.

### Scalar fields — 7/7 on all three documents

```
  field              correct   total     rate   tolerance
  ---------------- --------- ------- --------   ------------------------
  gstin                    3       3  100.0%   exact (critical)
  vendor_name              3       3  100.0%   normalised
  invoice_number           3       3  100.0%   exact
  invoice_date             3       3  100.0%   parsed date equality
  subtotal                 3       3  100.0%   Decimal +/- tol
  tax_total                3       3  100.0%   Decimal +/- tol
  grand_total              3       3  100.0%   Decimal +/- tol

  vendor_name, exact-string: 3/3 (100.0%)
```

Extraction and scoring both work end to end. That is the entire claim.

### The scorer was proven to actually detect errors

A scorer that returns 100% unconditionally looks identical to a correct one on clean data, so it was tested against deliberately corrupted input: one GSTIN character changed (`...R1ZX` → `...R1ZY`), one grand total shifted by 0.05, and one line item dropped.

```
gstin   : 2 / 3   (expected 2/3)
grand   : 2 / 3   (expected 2/3)
items   : synthetic_001_classic.png  expected 3, extracted 2
clean re-run, gstin: 3 / 3
```

It catches all three. The 100% above is a real result, not a vacuous one.

### Harness observation #1 — table recognition failed on the bordered layout

**This is an observation about the harness run, not a finding about accuracy.** It is recorded because it generates a hypothesis worth testing deliberately against real invoices.

Line-item extraction:

```
  correct item COUNT: 2/3 documents
  description correct: 7/7 (100.0%) of items compared
  amount correct:      7/7 (100.0%) of items compared
     synthetic_001_classic.png: expected 3, got 3; desc 3/3, amt 3/3
   ! synthetic_002_boxed.png:   expected 2, got 0; desc 0/0, amt 0/0
     synthetic_003_compact.png: expected 4, got 4; desc 4/4, amt 4/4
```

`synthetic_002_boxed.png` is the one fixture with a rectangle drawn around its header block. PP-Structure detected a table (`tables_detected: 1`) but returned a structure with the whole page collapsed into it and each *column* flattened into a single cell:

```html
<tr><td>Meridian Logistics Services GSTIN: 27AAGCM1234P1Z5</td></tr>
<tr><td>TAX INVOICE Invoice No: ML-8842 Invoice Date: 2026-05-02</td></tr>
<tr><td>Description Freight Chennai to Pune Loading and Handling</td><td></td><td></td></tr>
<tr><td>Qty 1 2</td><td>Rate 18,500.00 1,250.00</td><td>Amount</td></tr>
<tr><td>Subtotal IGST 18% Total</td></tr>
```

Every value is present — the OCR read everything correctly, which is why all seven scalar fields still scored — but the **row/column structure is wrong**, so no line item can be reconstructed from it. `"Rate 18,500.00 1,250.00"` is one cell where there should be two rows.

Three things worth being careful about before this is read as more than it is:

- **It is a synthetic fixture with an artificial border.** A drawn rectangle around a header is not the same stimulus as a real invoice's ruled table, and the failure may not reproduce on real documents at all.
- **It was not "fixed" in the parser deliberately.** A spatial fallback that reconstructs rows from OCR box positions would have made this fixture pass — and would have hidden exactly the behaviour the spike exists to measure. The raw table structure is instead written to `table_rows_raw` in every result, so a zero-item outcome is always attributable to table recognition vs. row parsing.
- **It is, however, directly relevant to open question #1.** Bordered and boxed layouts are common on real Indian invoices. Whether a surrounding rule confuses the wired-table cell detector is now a specific, testable question for the real evaluation rather than a vague worry about "layout variance".

### Throughput, noted but not a measurement

~33–52 seconds per single-page synthetic PNG on CPU, first-call model loading excluded. Recorded only because open question #5 asks for it; three clean single-page images on one laptop says nothing reliable about the real workload, and the two runs of the same three files differed by >50% (98.6s vs 154.8s total) depending on what else the machine was doing.

Formula, chart and seal recognition are disabled in `_load_pipeline()`. Left on, PP-StructureV3 downloads and loads `PP-FormulaNet_plus-L` among others — several hundred MB of model that no invoice needs. Table recognition stays on; it is what ADR 0008 chose this engine for.
